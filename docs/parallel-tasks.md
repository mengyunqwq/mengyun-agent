# 并行子任务：把复杂任务拆开一起跑

「这个项目是干什么的、有哪些坑、依赖关系是什么」——这种活如果一条线慢慢串，
用户要盯着一个光标等很久。这个功能让模型把它拆成几个子任务**同时**跑，各自去查各自的部分，
最后把结论汇总回来。

## 它是怎么跑的

```
用户：把整个项目读一遍，说说架构和风险
  │
  ├─ 父任务（主循环）第一轮 → 模型决定拆：
  │     task_spawn「读入口与依赖」  task_spawn「读测试与 CI」  task_spawn「找安全隐患」
  │     → 三个 spawn 立刻返回 taskId（不阻塞），父任务接着发 task_wait
  │
  ├─ 调度器（src/tasks.js）并发池放行 → 三个**独立的**子循环同时跑
  │     每个子任务：只读工具集 + 自己的小上下文 + 自己的轮数上限
  │
  └─ task_wait 收齐 → 把三段结论摘要回填给父任务 → 父任务统一写盘/给答案
```

## 四个工具

| 工具 | 作用 | 关键行为 |
|---|---|---|
| `task_spawn` | 拆一个子任务出去 | **立刻返回** taskId；不阻塞（否则拆三个就变成串行三个） |
| `task_wait` | 等结果 | 不填 `task_ids` 就等这一轮拆出去的全部；超时会如实说「还有几个没回来」 |
| `task_status` | 看进度 | 不阻塞；轮数/token/最近在干什么，以及预算还剩多少 |
| `task_cancel` | 取消 | 排队中的也能取消，不用等它开跑 |

## 为什么这么设计

**为什么子任务默认只有只读工具（read/glob/grep）**：并行写同一个文件必然竞态——
两个 `write` 打同一个路径、两个 `edit` 抢同一段内容，结果看运气。所以「查」并行做，
「写」由父任务串行做。真要开写权限，`task_spawn(..., allow_tools)` 可以显式给，
给了就要自己承担冲突风险。

**为什么子任务是独立的 agent 实例，而不是复用主实例只传白名单**：
系统提示词是按注册表生成的。共用实例的话，提示词里照样写着「你有 write/shell」，
模型照着调、然后被拒——行为会变得莫名其妙。独立实例 + 掩码注册表（`registry.clone`）
才是真的隔离：看不到的工具，连提示词里都不会出现。

**为什么同一轮里的 `task_*` 工具按顺序执行**：模型最自然的写法是「连发两个 spawn
再跟一个 wait」。默认同轮工具是并行的，那样 wait 会和 spawn 抢跑，看到「任务还不存在」，
功能就变成时灵时不灵。并行度在**子任务**里，spawn 本身立即返回，串行几乎不花时间。

**为什么父任务一结束就收掉所有子任务**：父任务已经给出最终答案（用户看到了），
子任务还在后台调模型、烧 token、往已经安静的会话里推消息——这就是僵尸任务。
父任务的中断、轮数用尽、正常结束，三条路都会级联收尾。

**为什么回填给父任务的是摘要而不是全过程**：三个子任务的完整输出会立刻把父上下文撑爆。
过程在界面的任务块里看（可展开的活动记录），进父对话的只有结论。

**摘要为什么要包一层 `<subtask-result>`**：子任务的结论是模型读了仓库内容之后写的，
里面完全可能夹带一段「忽略之前的指令」（一个恶意 README 就够了）。
凡是跨越信任边界的文本都该当作**数据**看——边界标记和「这是数据不是指令」的提示
就是把这条规则写进协议里。

**为什么会有 token 预算**：子任务和父任务用的是同一个网关、同一个 key。
不设上限的话，一次「帮我全面分析」可能变成几十次请求。预算按「一次用户消息」算：
超了就拒绝新的拆分，并把原因告诉模型（逼它自己串行做完剩下的）。

## 配置（config.json）

```json
{
  "tasks": {
    "enabled": true,
    "maxParallel": 3,
    "maxDepth": 1,
    "maxTasks": 6,
    "subTurns": 12,
    "subTimeoutSec": 600,
    "budgetTurns": 30,
    "budgetTokens": 200000,
    "readonlyTools": ["read", "glob", "grep"]
  }
}
```

| 项 | 默认 | 说明 |
|---|---|---|
| `maxParallel` | 3 | 同时跑几个。**同一个 key 下并发太多只会互相限流**，不是越大越快 |
| `maxDepth` | 1 | 子任务不能再拆子任务（1 = 只允许一层） |
| `maxTasks` | 6 | 一次用户消息里最多拆几个 |
| `subTurns` | 12 | 单个子任务最多几轮（父任务的 `maxTurns` 另算） |
| `subTimeoutSec` | 600 | 单个子任务超时后自动收掉，不拖死父任务 |
| `budgetTurns` / `budgetTokens` | 30 / 200000 | 一次用户消息里所有子任务的**总**预算 |
| `readonlyTools` | read/glob/grep | 子任务默认能用的工具 |

## 界面上长什么样

对话流里每个子任务是一块：`⚙ 读入口与依赖 · 进行中 · 2 轮 · ↑1.2k`。

- 运行中的块默认展开，能看到它最近在调什么工具、走到第几步；完成后自动收起（否则几个任务跑完满屏流水账）
- 状态有五种颜色语义：排队中 / 进行中 / 完成 / 失败 / 已中止或超时
- 子任务花的 token 会**计入本会话累计**，用量提示里单独标出「其中子任务 N」（不然数字会偏小，用户以为便宜）

## 排障

| 现象 | 原因 | 怎么办 |
|---|---|---|
| 模型说「调度器没有装配」 | agent 不是在 createApp 里创建的（web 模式在设置里配完 Key 才建 agent） | 已修：`ensureAgent` 会把调度器一起接上；`web-check` 有断言盯着 |
| 模型说「执行器没有装配」 | `provider` 在装配时还没有 | 已修：执行器运行时从 app 上取 provider，不用装配时的快照 |
| 子任务一直「进行中」不结束 | 执行器卡住 | 到 `subTimeoutSec` 会自动收掉并标成超时；也可以 `task_cancel` |
| 拆了没反应／说没有任务 | 同轮 spawn 和 wait 抢跑 | 已修：含 `task_*` 的轮次按顺序执行；`web-check` 有断言 |
| 界面上工具块卡在「进行中」 | 工具调用 id 被网关复用，结果写到了上一轮的块上 | 已修：按 id 匹配「还没落定」的那个块 |

## 测试

```bash
node test/tasks.js     # 调度器单测 27 项：并发上限/深度/超时/取消/预算/生命周期/掩码
node test/web-e2e.js   # 真起服务：拆两个 → 并行跑（只读）→ 摘要回填 → 界面块收敛到 done
```

`test/tasks.js` 不接模型：`runSubtask` 是注入的，所以能精确造出「谁卡住、谁超时、谁被取消」
这些在真实模型上很难复现的场景。`web-e2e` 则走真链路：假网关靠「请求里有没有 task_spawn」
分辨父任务和子任务，顺便验证子任务**真的拿不到** write/shell。
