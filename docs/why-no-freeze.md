# 界面为什么不再卡死


你之前遇到过「跑一个脚本，整个软件就卡住了」。那不是错觉，也不是电脑慢，是**三个平方级的坑叠在一起**——任意一层单独存在，都够把界面冻住：

| 层 | 原来干什么 | 为什么会卡 |
| --- | --- | --- |
| 后端 | 模型每吐一个分片，就把**到目前为止的完整正文**广播一次 | 第 k 个分片要重发前面全部内容，总字节量随长度**平方**增长 |
| 前端 | 每收到一条，就把整段正文**重新解析一遍 Markdown**、重建 DOM | 同样平方级；几万字的回答足以把主线程占满好几秒 |
| 进程 | 脚本在死循环里刷日志时，输出被无限拼进内存字符串 | 内存一路上涨，SSE 被刷爆，界面跟着定格 |

### 现在怎么处理的

**1. 后端合帧**（`src/web/server.js`）

同一个块的连续 `text` / `reasoning` 事件在 30ms 内只保留**最后一条**（它本来就是最全的那条），到点或遇到其它类型的事件时立刻冲刷。顺序不会乱：`text_end` 一定排在正文后面。网络字节量从平方级降到线性。

再加一道**背压保护**：浏览器消费不过来时 socket 会一直攒数据，攒到几百 MB 就是内存爆掉。积压超过 1MB 就丢弃「可丢的流式帧」——丢一帧不心疼，下一帧就是更全的全文；但工具结果、报错这类一次性事件一帧都不丢。

**2. 前端按帧合并重绘**（`web/app.js`）

```
原来：每个分片一条 → 立刻全量重解析 Markdown + 重建 DOM

现在：每个分片一条 → 登记一次重绘 ─┐
                                  ├─ 每帧最多真正画一次，而且只画最新的那条
      50ms 内来 100 条 ───────────┘
```

超过 12000 字的正文在**流式期间先按纯文本铺**（`textContent` 几乎不花时间），等这一块定稿了再一次性解析成 Markdown。工具输出按头尾截断、中间省略并注明省了多少——DOM 体积始终有上限，但**最后那行报错永远看得见**。

**3. 进程级熔断**（`src/tools/builtin.js`）

- 一次命令的输出超过 **512 KB** 就直接杀掉进程，并明确告诉你「多半是脚本在死循环里刷日志」
- 命令的 **stdin 接空设备**：脚本里若有 `Read-Host` / `pause` / `read` 这类交互等待，会立刻拿到 EOF，而不是把命令一直挂到超时
- 超时用 `taskkill /T /F` **连子进程一起杀**。只杀 PowerShell 的话，它拉起的 node / npm 会变成孤儿继续跑，端口和文件锁都不释放——那才是「明明停了，软件还是动不了」的根源
- Windows 上强制 PowerShell 按 **UTF-8** 输出，中文脚本日志不再乱码

**4. 顺手修掉的一处**：消息区原来开着 `scroll-behavior: smooth`。流式输出时我们每 50ms 就要把视图拉到底，而平滑滚动是几百毫秒的动画，高频调用会让动画永远被下一次打断——表现出来同样是「滚不动 / 像卡死」。现在改成瞬间定位。

### 怎么验证

```bash
npm run freeze-test
```

这个测试不只看代码里有没有那几行防护，它会**真跑一个死循环刷屏的脚本**确认几秒内被熔断，再跑一个等 stdin 的脚本确认它不会挂到超时。
